# ADR 0043: Registries are released data interfaces

- **Status:** Accepted
- **Date:** 2026-11-07
- **Supersedes:** [ADR 0037](0037-the-repository-adopts-engineering-conventions-0-7-0.md) §3, core's lone record
- **Refines:** [ADR 0022](0022-the-musher-document-core-specification.md) §5, core ships no document schema
- **Relies on:** [ADR 0023](0023-published-bytes-are-immutable-release-assets.md), immutable release assets
- **Relies on:** [ADR 0038](0038-v2-one-vocabulary-and-v1-retires.md), the term records
- **Relies on:** [ADR 0042](0042-the-repository-adopts-engineering-conventions-0-9-3.md), engineering-conventions 0.9.3

## Context

Every fact a consumer needs about a Musher document family is written in a
`spec.md`: the requirement IDs, the diagnostic codes and the phases that report
them, the validation phases, scopes and statuses, the resolution stages, the
reserved namespaces. The term records in `docs/terminology.yaml` add the
vocabulary. None of it is released as data. A release archive carries the
prose, and a consumer that needs a code list parses Markdown or copies it by
hand ([#217](https://github.com/musher-dev/specifications/issues/217)).

Both happen. platform-api copies the spec's regular expressions, ports the
diagnostics table by hand, and invents a severity the specification did not
define. musher-cli carries its own copy of the phases. Each copy drifts the day
a table changes, and nothing in either repository notices.

The engineering conventions already have a place for this. EC-0030 declares a
`data` interface: "one or more JSON or YAML documents that are the published
fact themselves: a registry, a vocabulary". EC-0031 says what a `gated` data
interface's `contracts:breaking` compares: the members a consumer relies on,
where a released member that is gone, or a value that changed, is a break.
EC-0033 names the `dependency-released` dispatch a consumer's
maintain-dependencies workflow answers.

Two earlier decisions stand in the way as written. ADR 0037 §3 says a core
archive carries `specification.json` alone, because core delivers no interface
and the release record needs one. ADR 0022 §5 says core ships no schema, which
was written about the document envelope and reads as forbidding any JSON Schema
in core.

## Decision

### 1. Each family version carries a registry

Each family version directory gains `registry/`, released with it:

| File | In | Holds |
|---|---|---|
| `requirements.json` | every family | The family's own requirement IDs, each as `{id, anchor, section}`: the ID, the fragment locating it in `spec.md`, and the anchor of the section stating it. |
| `diagnostics.json` | every family | Every code a document of the family may report: core's, then each normative dependency's in §2's order, then its own, each as `{code, phases, severities, declaredBy}`, with `requirement` for a warning. |
| `vocabulary.json` | core | The ordered phases, the scopes with the phases each runs, the result statuses, the severities `ERROR` and `WARNING`, the ordered resolution stages, and the reserved namespaces, each with whether it is assigned. |
| `terms.json` | core | Every term record. |

`diagnostics.json` is the resolved reach, the same set the conformance runner
lets a corpus declare, so an implementation reads one file rather than
resolving §2 itself. A diagnostics table row gives `severities: ["ERROR"]` and
its phases. A warnings table row ([ADR 0044](0044-the-validation-result-is-a-released-schema.md))
gives `severities: ["WARNING"]` and every phase, because a warning is reported
by whichever phase checks the requirement it names.

Each file's schema is in core, under `interfaces/registry/`:
`requirements.schema.json`, `diagnostics.schema.json`,
`vocabulary.schema.json` and `terms.schema.json`, each with an `$id` under
`https://specifications.musher.dev/core/v2/registry/`. The term records' schema
moves there from `docs/`, and `docs/terminology.yaml` names it for editors.

### 2. A registry is a committed projection, and spec.md stays normative

Each registry file is generated by `task docs` (`tools/src/render/registry.ts`)
and committed, as `docs/traceability.md` is. A release carries the committed
bytes, and `release:stage` reads them at the tag like every other byte.

`spec.md` remains the definitive statement of every requirement ID, code,
phase, stage and namespace. A registry restates it and is never a second
source. Drift between the two is a check failure, not a disagreement to
resolve: `task check:docs` regenerates every file in memory and fails when a
committed copy differs, and `task contracts:check` runs it. Were a stale file
ever released, the prose would govern, as it governs every other disagreement
([What is normative](../../specifications/README.md#what-is-normative)).

### 3. The term records ship in core

`terms.json` holds every record of every context in core's registry, rather
than each family's records in its own. A record's context is not a family:
`catalog`, `deployment` and `repository` are contexts no family owns, and a
blueprint record cites component's concepts. Splitting the file would invent
an owner for each of them.

The consequence is accepted: every edit to `docs/terminology.yaml` changes
core's `registry/terms.json`, so it is a releasable change to core and enters
core's next release. A `docs` commit that edits a record is a core release set.

### 4. Core delivers interfaces and a release record

From 2.1.0 a core archive carries `registry/` and `interfaces/` beside its
prose and corpus, and `release.json`, the conventions' release record of the
interfaces it delivers. This supersedes ADR 0037 §3: core now delivers
interfaces, so the record's one-interface minimum is met. An archive staged
for a core release before 2.1.0 is staged as it was published, with
`specification.json` alone.

This refines ADR 0022 §5. That section governs a schema for the document
envelope, and its reasons stand: a core document schema would either gate every
new family on a core release or assert nothing. A JSON Schema for what is not a
document, a registry or the validation result, is a different thing, and core
ships it in `interfaces/`, never in `schemas/`. `check:schema` still fails a
core `schemas/` directory, and lints every interface schema as it lints a
module: 2020-12, an `$id` under the family version, every reference local, and
every object closed.

The release record lists each file of an interface with its own SHA-256. A
kind family's schema interface is one member, the bundle; a registry is one
member per file. A kind family archive carries its dependencies' registries
and interfaces under their family names, as it carries their prose.

### 5. The declarations

`.repo/outputs.toml` declares, all `gated` and `public`:

| Interface | Format | Definitions | Delivered by |
|---|---|---|---|
| `core-validation-result` | `json-schema` | `interfaces/validation-result.schema.json` | `core-release` |
| `core-registry-schemas` | `json-schema` | `interfaces/registry/` | `core-release` |
| `core-registry` | `data` | `registry/` | `core-release` |
| `component-registry` | `data` | `registry/` and `protocols/` | `component-release` |
| `blueprint-registry` | `data` | `registry/` | `blueprint-release` |
| `blueprint-connection-evidence` | `json-schema` | `interfaces/connection-evidence.schema.json` | `blueprint-release` |
| `listing-registry` | `data` | `registry/` | `listing-release` |

Each path is under `specifications/<family>/v2/`. The registries are
`generated`, so `contracts:generate` exists and runs `task docs`. Component's
protocol records ([ADR 0045](0045-connection-protocols-are-a-registry.md)) are
authored, and travel in `component-registry` because a consumer reads them with
the member lists they define.

### 6. A part has a floor

`tools/src/lib/layout.ts` names `registry`, `interfaces` and `protocols` as
parts of a family version, the families that carry each (`interfaces` core and
blueprint, `protocols` component), and a floor, `PART_SINCE`, of `2.1.0` for
all three. A release at or after its part's floor must carry it, and a tool
reading the tag fails when it is absent, as for `spec.md`. A release before the
floor does not carry it, so `check:published`, `site:fetch`, `release:stage`
and the compatibility gates still read every 2.0.0 tag unchanged.

### 7. A data interface is held to its last release

`task check:compat:registry`, run by `contracts:breaking` and `task check`,
compares each family version's `registry/`, `interfaces/` and `protocols/` with
the same files at its newest tag, offline:

- every released requirement ID survives with the same anchor;
- every released code survives, and its phases and severities never shrink;
- each vocabulary list keeps every released entry in its released position, so
  a list grows only at its end; a scope's phases never shrink, and an assigned
  namespace stays assigned;
- every released term record survives and claims every identifier it claimed;
- every released protocol and category survives, each released member is
  unchanged, and a new member is never required;
- in an interface schema every released property survives, `required` never
  grows and an enum keeps every released value. The validation result's enums
  are frozen outright, because a consumer switches on its status and severity.

A family version whose newest release predates 2.1.0 has nothing to compare.
Like `check:compat`, this guards a major version: a break needs a new `v<N>`.

### 8. A release notifies its consumers

`.github/workflows/notify-release.yml` runs on `release: published`, which
release.yml's App-published releases trigger, and by hand for a tag. It checks
the tag is a published family release carrying its archive and `SHA256SUMS`,
then sends the `dependency-released` repository dispatch to platform-api and
musher-cli, with `client_payload` `{repository: "specifications", output:
"<family>-release", version}`, using `DEPENDENCY_DISPATCH_TOKEN`. Without that
secret it ends green with a notice: each consumer also syncs on a schedule, so
a missing dispatch delays a pin and loses nothing.

### 9. The site does not serve the registries yet

The site serves pinned bytes only from verified release assets. Serving a
registry at a pinned URL means reading it out of the verified archive, with an
alias, a `_headers` rule and an inventory for each file. That is left to a
later change. Until then a consumer reads the registries from the release
archive, and the interface schemas' `$id`s are names, not yet URLs that
resolve.

## Consequences

- Consumers vendor a family's archive and read its registries instead of
  parsing Markdown. The follow-up issues for platform-api, musher-cli and the
  SDKs replace their copies.
- Every family's next release is 2.1.0, the first to carry a registry, and
  core's is the first with a release record.
- Every term record edit is a core release set (§3).
- A change that removes or narrows a released member fails
  `contracts:breaking`, which before this decision only replayed documents.
- `docs/publication.md`, `docs/using-schemas.md`, `specifications/README.md`
  and `specifications/core/README.md` no longer say that core ships prose
  alone.

## Alternatives considered

- **Each family's term records in its own registry.** Rejected (§3): most
  contexts belong to no family, and a split file needs an owner for each.
- **The registry as the normative source, with tables generated into
  spec.md.** Rejected for requirements and codes: a requirement is a sentence
  in the prose, and moving its source out of the prose moves the rule away from
  the reasoning that states it. ADR 0045 makes the opposite choice for the
  protocol registry, whose records are data with no prose of their own.
- **Projections built at release time and never committed.** Rejected: the
  bytes a release carries would then exist nowhere a reviewer reads before the
  tag, and `check:published` could not tie them to a tree.
- **Serving the registries on the site now.** Deferred (§9), because pinned
  serving reads only verified assets, and no release carries a registry yet.
